# Cloud1 — оценка ковенантов из кредитных договоров

Система читает PDF кредитных договоров, извлекает из них финансовые условия (**ковенанты**),
проверяет их по реестру транзакций и выдаёт ответ с доказательством.

**Cloud1** — третья архитектура в этом репозитории, после `codex-1` и `codex-2`.
Она не переписывает систему, а переставляет один узел и за счёт этого начинает ловить
класс ошибок, невидимый для предшественников.

```bash
cd 2_ARCHITECTURE_COVENANT_MVP && python scripts/cloud1_demo.py
```

Демо не требует ни ключей, ни интернета, ни Docker.

## 1. Что решает система

Банк выдаёт кредит компании. В договоре записаны условия, которые заёмщик обязан соблюдать:

> «Совокупный месячный объём исходящих платежей в KZT не должен превышать 15 000 000 KZT»

Задача: по каждой паре **(заёмщик, ковенант)** выдать три поля.

| Поле | Что это | Пример |
| --- | --- | --- |
| `verdict` | соблюдён или нарушен | `violated` |
| `number` | число, на котором основано решение | `16000000.000000` |
| `evidence` | транзакция-улика, если нарушение привязано к операции | `TX-A2` |

| Вход | Формат |
| --- | --- |
| Кредитные договоры | PDF, в том числе сканы и таблицы |
| Реестр транзакций | CSV / XLSX / Parquet |
| Вопросы организатора | JSON |

## 2. Идея в одном экране

Ядро унаследовано от `codex-1` и не менялось: **LLM понимает текст, но не считает.**

```
┌─ ИНТЕРПРЕТАЦИЯ ─ здесь работает LLM ──────────────────────┐
│                                                            │
│  PDF → OCR → детектор находит пункты договора             │
│                     ↓                                      │
│  LLM переводит текст пункта в структуру CovenantSpec:     │
│                                                            │
│     «Выручка не ниже 50 млн тенге в месяц»                │
│        ↓                                                   │
│     metric:    SUM(amount)                                 │
│     filter:    direction = incoming, currency = KZT        │
│     window:    calendar_month                              │
│     operator:  >=                                          │
│     threshold: 50000000                                    │
└────────────────────────────────────────────────────────────┘
                            ↓
                      CovenantSpec
                            ↓
┌─ ВЫЧИСЛЕНИЕ ─ LLM не участвует вообще ────────────────────┐
│                                                            │
│  CovenantSpec + транзакции в DuckDB                       │
│        ↓                                                   │
│  SQL → число → сравнение с порогом → вердикт              │
│        ↓                                                   │
│  подбор доказательства → верификация → submission.json    │
│                                                            │
│  Одни и те же входные данные → всегда один и тот же ответ │
└────────────────────────────────────────────────────────────┘
```

Модель хорошо читает текст и плохо считает. SQL наоборот. Каждый занят своим.

## 3. Что Cloud1 меняет

### Проблема, найденная аудитом

Ошибиться можно на четырёх шагах, и проверки стояли не там:

```
                  обнаружение  интерпретация  исполнение
                  ───────────  ─────────────  ──────────
частота ошибок      высокая       высокая       низкая
как проявляются   молчаливо     молчаливо      громко
проверок было         нет       почти нет    четыре слоя
```

Ошибка исполнения падает с исключением — её видно сразу. Ошибка интерпретации даёт
аккуратное число с доказательством и правильным вердиктом; всё выглядит верно, кроме того,
что посчитано не то.

`codex-2` первым это заметил и посадил модель-ревьюера читать текст пункта рядом со
спецификацией. Правильная идея — поставленная **после** вычисления, где её вывод уже нельзя
использовать. Замечание уходило в файл, который никто не читает.

### Решение

Ревьюер переезжает на шаг раньше и получает петлю с проверкой контекста:

```
        компиляция
             │
          review ──принято──────────────────────────────► реестр
             │
        отклонено
             ↓
      grade_context  ← «модель ошиблась в прочтении
             │           или в контексте не было ответа?»
    ┌────────┴────────┐
хватало           НЕ хватало
    │                 │
    │         expand_retrieval  ← повторный поиск
    │                 │            по запросу грейдера
    └────────┬────────┘
             ↓
        recompile
             ↓
          review (2-й проход) ──────────────────────────► реестр
```

Разделение двух причин принципиально: если пункт ссылается на сноску, которой не было в
контексте, перекомпиляция с тем же контекстом **не может** помочь никогда.

Границы жёсткие и структурные, а не эвристические: **ревью ≤ 2, грейдингов ≤ 1,
расширений ≤ 1, перекомпиляций ≤ 1.** Проверяется тестом.

### Что это даёт

| | codex-2 | Cloud1 |
| --- | --- | --- |
| Когда работает ревьюер | после вычисления | **до вычисления** |
| Что видит | ответ, число, вердикт | текст пункта, спецификация, контекст |
| Может изменить число | нет — держит валидатор | **нет — числа ещё не существует** |
| Вызовов LLM на ревью | `P … 2P` за каждый прогон | `C … 2C` всего, кешируется |
| Пример: 12 ковенантов, 40 пар, 3 прогона | 120 … 240 | 12 … 24 |
| Влияние на балл | ноль по построению | **прямое** |

Дешевле, безопаснее — и единственный вариант, способный ответ улучшить.

### Плюс исправления

| Что было сломано | Стало |
| --- | --- |
| Проверка полноты сравнивала список сама с собой и не могла сработать никогда | Ожидания строятся до оценки из вопросов организатора |
| У групповых ковенантов все заёмщики получали один `calculation_id`, записи затирались | `borrower_id` всегда входит в хеш |
| «Гибридный» поиск молча работал как поиск по ключевым словам | Эмбеддер проверяется пробным вызовом, деградация логируется |
| Детектор знал только английский и русский | Добавлен казахский |
| Число, сохранённое как доказательство, никогда не перепроверялось | Двойной путь вычисления |

## 4. Доказательство на живом прогоне

Прогон против настоящего DeepSeek на синтетическом наборе. Модель скомпилировала
8 ковенантов из PDF; результат сверен с эталоном.

| Ковенант | Эталон | Модель выдала | Ревьюер |
| --- | --- | --- | --- |
| COV-ALPHA-COUNT | count | count | `accepted` |
| **COV-ALPHA-MAX** | **max** | **sum** ← ошибка | **`low`** |
| COV-ALPHA-MIN | min | min | `accepted` |
| COV-ALPHA-SUM | sum | sum | `accepted` |
| COV-BETA-AVG | avg | avg | `accepted` |
| COV-BETA-MAX | max | max | `accepted` |
| COV-BETA-SUM | sum | sum | `accepted` |
| COV-GAMMA-SUM | sum | sum | `accepted` |

**7 верных — все приняты. 1 неверный — помечен. Ноль ложных срабатываний в обе стороны.**

Текст пункта: «Один исходящий перевод в KZT не может превышать 5.000.000 KZT».
Модель прочитала «один» как «суммарно за месяц» и выдала `sum`. Возражение ревьюера:

> The metric type 'sum' aggregates all outgoing KZT transactions in the month, but the
> covenant states that **each individual** outgoing transaction must not exceed 5,000,000 KZT.

Без Cloud1 эта пара дала бы уверенный неправильный ответ. С Cloud1 она стоит первой в
списке на разбор:

```
ранг  уровень   доверие    пара
1     low       low        B001/COV-ALPHA-MAX   ← сюда смотреть
2     high      accepted   000777/COV-GAMMA-SUM
3     high      accepted   B001/COV-ALPHA-COUNT
```

## 5. Быстрый старт

### Демо без ключей

```bash
cd 2_ARCHITECTURE_COVENANT_MVP
```

```bash
python scripts/cloud1_demo.py
```

Прогоняет весь пайплайн на моковых данных и сверяет с эталоном: **10 из 10**.
Возвращает ненулевой код при расхождении, поэтому годится как проверка перед реальным запуском.

### Тесты

```bash
docker compose --profile test run --rm test
```

### Реальный прогон

Ключ в `.env` (файл в git не попадает):

```dotenv
DEEPSEEK_API_KEY=sk-...
LANGSMITH_API_KEY=lsv2_...
LANGSMITH_PROJECT=halyk-covenants
LANGSMITH_TRACING=true
```

Данные — в `data/raw/`: PDF в `documents/`, таблицы в `transactions/`.

```bash
halyk-covenants preprocess data/raw --db data/run.duckdb
```

```bash
halyk-covenants evaluate-all --at-date 2026-08-05 --db data/run.duckdb --questions data/questions.json --output data/results.json --confidence-output data/confidence.json
```

Форматы файлов, все флаги и разбор проблем — в [RUNBOOK.md](docs/architecture-v3/RUNBOOK.md).

### Сравнить с codex-1 без переключения веток

```bash
halyk-covenants preprocess data/raw --db data/base.duckdb --no-spec-review
```

Разница между результатами — вклад Cloud1.

## 8. Состояние проекта

### Работает и проверено

```
263 теста, ruff чистый
демо на моковых данных: 10/10
живой прогон DeepSeek:  8 ковенантов из PDF, ревьюер 7/7 и 1/1
трейсы LangSmith:       узлы графа с метаданными решений
```

### Что осталось

| Задача | Почему важно |
| --- | --- |
| Вопросы как **обязательный** вход | Сейчас `--questions` необязателен. Пара, о которой спросили, но которую система не нашла, должна давать строку со статусом ошибки, а не отсутствовать |
| Параллельные вызовы LLM | При 50 ковенантах последовательная компиляция не укладывается в трёхчасовой регламент — превышение примерно вдвое |
| Откат при поломке таблицы | Цепочка `native → layout → ocr` не имеет возврата к сырому тексту, если распознавание таблицы сломало структуру |

Подробности и оценки — в [PLAN_HACKATHON.md](docs/architecture-v3/PLAN_HACKATHON.md).

### Известные ограничения

- 16 из 279 тестов требуют шрифты DejaVu и проходят только в контейнере
- Ковенант, который не нашёл детектор и о котором не спросил организатор, остаётся невидимым
  для любой автоматической проверки — Cloud1 сужает эту слепую зону, но не закрывает
- Ревьюер спецификаций не увидит ошибок, проявляющихся только на данных; такие ловятся
  детерминированно через флаг `empty_input_rows` и двойной путь вычисления
