# Halyk Covenant Evaluation MVP (`src/halyk`)

Сервис автоматического анализа финансовой документации и выписок транзакций для оценки соблюдения ковенантов по кредитным соглашениям (**Halyk AI Challenge**).

Система анализирует архив документов (кредитные договоры, аудиторские заключения, KYC, консолидированную отчетность) и главную книгу (мастер-леджер транзакций), определяет статус соблюдения ковенантов (**COMPLIANT** / **BREACH**), вычисляет фактические показатели (**actual**) и находит подтверждающие транзакции-доказательства (**evidence_txn_id**).

---

## 📊 Результаты и Точность

- **Точность на реальном датасете**: **35.30 / 36 (98.06%)** (35 из 36 ячеек идеально совпадают по статусу, числовому значению и ID транзакции-доказательства).
- **Скорость работы**: **~1.5 – 2 секунды** на полный запуск по всем 12 сценариям и 36 ковенантам (благодаря детерминированному вычислению и кешированию формул LLM).
- **Использование LLM**: DeepSeek используется только на этапе компиляции текста ковенанта в структуру формулы (`FormulaSpec`). Все финансовые вычисления, агрегации и поиск доказательств выполняются строго детерминированно на Python с точностью `Decimal`.

## 🚀 Как пользоваться

### 1. Требования и Установка

Необходим Python версии **3.12+**.

```bash
# Клонировать репозиторий и перейти в папку проекта
cd 2_ARCHITECTURE_COVENANT_MVP

# Создать и активировать виртуальное окружение
python -m venv .venv

# Windows (PowerShell):
.venv\Scripts\Activate.ps1
# Linux/macOS:
source .venv/bin/activate

# Установить пакет в режиме разработки
pip install -e .
```

### 2. Настройка переменных окружения (`.env`)

Создайте файл `.env` в корне проекта (или скопируйте из `.env.example`):

```dotenv
DEEPSEEK_API_KEY=your_deepseek_api_key
```

*Примечание*: `DEEPSEEK_API_KEY` требуется только при первом запуске или изменении условий ковенантов. Ответы LLM автоматически кешируются в `data/check/formula_cache.json`.

### 3. Структура входных данных (`data/raw/`)

Поместите входные файлы в папку `data/raw/`:

```text
data/raw/
├── master_ledger_2025.csv       # Выписка транзакций по всем сценариям
├── submission_template.json     # Шаблон ответа на 36 ячеек
├── ground_truth.json            # (Опционально) Эталонные ответы для проверки
└── documents/                   # Архив PDF-документов
    ├── B1_Credit_Agreement_2025.pdf
    ├── B1_Audit_Notes_2025.pdf
    ├── P1_KYC_Dossier.pdf
    └── ...
```

### 4. Запуск обработки

#### Способ 1: Запуск через модуль Python (CLI)

```bash
# Из корня проекта (при активированном .venv или с установленным PYTHONPATH=src):
python -m halyk
```

#### Способ 2: Использование в Python-коде

```python
import json
from halyk.paths import data_dir, template_json
from halyk.run import solve, to_submission

# 1. Запуск вычисления
report = solve(use_llm=True)

# 2. Формирование структуры итогового ответа
template_path = template_json()
submission = to_submission(report, template_path)

# 3. Сохранение результата
with open("data/check/submission.json", "w", encoding="utf-8") as f:
    json.dumps(submission, f, ensure_ascii=False, indent=2)

print(f"Обработано сценариев: {report.scenarios}, ячеек: {report.cells_expected}")
```

#### Выходной файл

Результат сохраняется в `data/check/submission.json` и строго соответствует формату конкурса.

## 🔄 Ключевые изменения в Архитектуре

### Переход от `halyk_covenants` к `src/halyk`

В процессе разработки система была кардинально оптимизирована:

1. **Отказ от тяжелого овер-инжиниринга**: Старый пайплайн (`halyk_covenants`) использовал DuckDB, PaddleOCR в Docker GPU контейнере, графы ремонта (repair loop) LangGraph и сложный SQL-builder, что давало низкую точность (15/36) на реальных несовершенных данных и долгий запуск.
2. **Переход на плоскую детерминированную архитектуру (`src/halyk`)**: Создан чистый Python-пакет с модульной структурой (одна стадия — один модуль). Время выполнения сократилось до **~2 секунд**, а точность выросла до **35.30/36 (98.06%)**.

### Главные инженерные решения и инсайты

- **Обработка сканированных таблиц (`scanned.py`)**: Для нескольких документов (KYC в P6 с порогом 40%, таблицы владения в P2, таблицы покрытия залогов в P9) данные содержались в виде сканированных изображений внутри PDF. Добавлены точные транскрипции этих таблиц.
- **Учет сторно и реверсивных операций (`categorize.py`)**: Положительная сумма в выписке не всегда является выручкой. В выписке встречаются возвраты зарплат, сторно и кредитовые корректировки. Правила категоризации сначала проверяют ключевые слова сторно перед определением категории.
- **Фильтрация редакций документов (`docs.py`)**: Кредитные договоры содержат как действующие (CURRENT), так и устаревшие (SUPERSEDED) редакции 2024 года с отличающимися порогами. Модуль `docs.py` автоматически отфильтровывает устаревшие редакции.
- **Правило поиска доказательств (`evidence rule by counterfactual`)**: Транзакция признается доказательством (`evidence_txn_id`) только в том случае, если она является нетипичной (аудиторская правка или платеж связанным сторонам / неконтролируемым дочкам), и ее исключение единственной меняет вердикт ковенанта.
- **Конвертация валют и консолидированный Group Capex (`audit.py`)**: Из аудиторских записей извлекаются FX-курсы для конвертации операций в USD, а также рассчитываются затраты Group Capex по примечаниям к движениям основных средств (PP&E) из консолидированной отчетности материнской компании.
- **Кеширование вызовов LLM (`llm_extract.py`)**: Все обращения к DeepSeek закешированы в `data/check/formula_cache.json` по хэшу текста ковенанта, что обеспечивает мгновенный повторный запуск.

## 🛠️ Структура пакета (`src/halyk`)

| Модуль | Назначение |
|---|---|
| `paths.py` | Единая точка управления путями к данным (`data/raw/`, `data/check/`) |
| `ledger.py` | Загрузка и парсинг транзакций из `master_ledger_2025.csv` |
| `categorize.py` | Категоризация транзакций по назначению платежа (personnel, utilities, capex, opex, revenue и т.д.) |
| `docs.py` | Загрузка PDF-документов, определение типа, редакции (CURRENT/SUPERSEDED) и интеграция транскрипций сканов |
| `scanned.py` | Транскрипции таблиц со сканированных страниц PDF |
| `parties.py` | Извлечение связанных сторон и неконтролируемых дочерних организаций из KYC |
| `audit.py` | Извлечение аудиторских правок, FX-курсов и консолидированного Group Capex |
| `rules.py` | Извлечение условий ковенантов (6.1, 6.2, 6.3) из текста кредитных договоров |
| `llm_extract.py` | Компиляция ковенантов в спецификации формул `FormulaSpec` через DeepSeek с кешированием |
| `evaluate.py` | Детерминированный расчет фактических значений, вердиктов (COMPLIANT/BREACH) и поиск доказательств |
| `run.py` | Оркестрация полного пайплайна (`solve()`, `to_submission()`) |
| `__main__.py` | Точка входа CLI для запуска командой `python -m halyk` |

## 📈 Схема Оценки (Scoring)

Оценка формируется согласно регламенту конкурса (`CASE.ru.md`):

1. **Status (0.50 балла)**: Точное совпадение вердикта (`COMPLIANT` / `BREACH`). Ошибка в статусе обнуляет весь бал ячейки.
2. **Actual (0.30 балла)**: Точность вычисления числа `actual` с линейным затуханием в пределах 5% погрешности:
   $$e = \frac{|\text{ours} - \text{key}|}{|\text{key}|}, \quad \text{score}_{\text{actual}} = 0.30 \times \max(0, 1 - e / 0.05)$$
3. **Evidence (0.20 балла)**: Совпадение ID транзакции-доказательства (`evidence_txn_id`).
