# Covenant Evaluation MVP Phases 1–3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a runnable Python MVP that validates covenant rules, loads normalized transaction files into DuckDB, and deterministically evaluates SUM, COUNT, MAX, MIN, and AVG covenants.

**Architecture:** Keep domain schemas independent from persistence and execution. `DuckDBStore` owns raw/canonical transaction ingestion, SQL helpers compile only allowlisted fields and operators, evaluator classes compute exact values and delegate verdicts to one comparator engine, and the CLI composes these units without containing business logic.

**Tech Stack:** Python 3.12+, Pydantic 2, Pydantic Settings, DuckDB, Pandas/OpenPyXL for Excel input, Typer, PyYAML, pytest, Ruff.

## Global Constraints

- Implement only architecture Phases 1–3; PDF, OCR, LLM, vector retrieval, and agent orchestration are out of scope.
- Money uses Python `Decimal` and DuckDB `DECIMAL(38, 6)`; never use floating-point arithmetic for covenant values.
- Transaction, borrower, account, and source-row identifiers remain strings, including leading zeroes.
- Each evaluator returns a `CovenantResult`; exceptions are isolated as `failed` results by the evaluator service.
- MAX may return the maximum transaction as evidence; aggregate SUM/COUNT/MIN/AVG rules do not invent evidence.
- Tests must demonstrate comparator boundaries, filters, time windows, empty-set semantics, evidence selection, and partial-result behavior.
