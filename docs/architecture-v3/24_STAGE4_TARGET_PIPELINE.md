## 1. Три факта, задающие форму

### Ф-1. Задача крошечная

```
36 ячеек · 12 сценариев · 673 значимые строки · 36 значимых документов
199 КБ CSV · 843 страницы PDF
```

Пропускная способность не является проблемой. Единственный дорогой ресурс — **вызовы LLM**.
Любая архитектура, оптимизирующая throughput, решает несуществующую проблему.

### Ф-2. Пустая ячейка стоит столько же, сколько неверная

Из CASE: «Пустая и неверная ячейка стоят одинаково, поэтому заполняйте все ячейки.»

Отсюда **правило системы**: конвейер обязан выдать ответ на каждую из 36 ячеек при любом сбое.
Отказ — не вариант. Это переворачивает обычную логику обработки ошибок: fatal-ошибок почти нет,
есть деградация до наилучшей доступной догадки.

### Ф-3. Улика определяется контрфактически, и это подтверждено эталоном **[OBS]**

```
P5 6.3  actual = 273 418.66   улика TXN-P5-0004 = −273 418.66
P7 6.3  actual = 291 663.82   улика TXN-P7-0035 = −291 663.82
P9 6.3  actual = 268 447.19   улика TXN-P9-0040 = −268 447.19
```

`actual` в точности равен модулю суммы улики: вся величина ковенанта состоит из одной операции.
Убрать её — метрика обращается в ноль, вердикт переворачивается. Все 9 улик стоят только у
`BREACH`; 27 ячеек имеют `null`.

Следствие: улика **вычисляется перебором**, а не угадывается эвристикой. При ≤59 строках на
сценарий это ≤59 пересчётов на ячейку — на DuckDB бесплатно.

**K-06 закрыт.**

## 2. Proposed architecture

```
┌── ФАЗА A · ЗАГРУЗКА ─────────── детерминированно, без LLM ──────────────┐
│  A1  ingest_ledger      CSV        → RawLedgerRow[]                     │
│  A2  ingest_documents   файлы      → RawDocument[]                      │
│  A3  load_template      JSON       → CellKey[36]                        │
└─────────────────────────────────────────────────────────────────────────┘
                                   ▼
┌── ФАЗА B · ИНТЕРПРЕТАЦИЯ ─────── единственная фаза с LLM ───────────────┐
│  B1  route_documents    RawDocument → DocumentRecord{type,scenario,     │
│                                        edition}          ← LLM/правила  │
│  B2  extract_clauses    действующий договор → ClauseText[3]  ← LLM      │
│  B3  extract_adjustments аудит → Reclassification[]          ← LLM      │
│  B4  extract_parties    KYC → RelatedParty[] + порог         ← LLM      │
│  B5  categorize         description → Category               ← LLM      │
│  B6  compile_rule       ClauseText → CovenantRule            ← LLM      │
│  B7  review_rule        CovenantRule + текст → принять/чинить ← LLM     │
└─────────────────────────────────────────────────────────────────────────┘
                                   ▼
┌── ФАЗА C · РАСЧЁТ ────────────── LLM не участвует ──────────────────────┐
│  C1  normalize_ledger   RawLedgerRow → LedgerEntry                      │
│  C2  apply_adjustments  LedgerEntry + Reclassification → LedgerEntry'   │
│  C3  evaluate           CovenantRule + LedgerEntry'[] → actual, status  │
│  C4  find_evidence      контрфактический перебор → evidence_txn_id      │
│  C5  verify             двойной путь · манифест · границы               │
│  C6  emit               CellAnswer[36] → submission.json                │
└─────────────────────────────────────────────────────────────────────────┘
                                   ▼
                          submission.json  →  скоринг организатора
```

**Слои, которых нет и не будет.** SERVICE / API — потребитель один, автоматический скорер;
HTTP-слой не решает никакой задачи. Отдельный VALIDATION-этап — валидация происходит на каждой
границе как проверка контракта, а не как отдельный проход. Отдельный PERSISTENCE-этап — DuckDB
является подложкой всех фаз, а не шагом.

## 3. Canonical internal representation

### Граница raw ↔ domain

```
RAW      побайтово верно источнику, ничего не интерпретировано
         RawLedgerRow, RawDocument
         ── ГРАНИЦА ──  здесь и только здесь появляется интерпретация
DOMAIN   LedgerEntry, DocumentRecord, CovenantRule, CellAnswer
```

Правило: **raw хранится всегда и никогда не перезаписывается.** Любая производная величина
воспроизводима из raw + зафиксированных решений интерпретации.

### Четыре доменных типа

```python
LedgerEntry
    txn_id        str            TXN-{scenario}-{nnnn}
    scenario_id   str            ВЫВЕДЕНО из txn_id, не из файла
    date          date
    counterparty  str
    description   str            сохраняется: источник категории
    amount        Decimal        со знаком, как в источнике
    currency      str            USD | EUR
    # производные, каждая — результат явного решения
    category            Category | None       ← B5
    category_source     Literal["model","audit","rule"]
    category_confidence float
    is_related_party    bool | None           ← B4
    amount_usd          Decimal | None        ← C1, если EUR
    is_noise            bool                  scenario_id ∉ 12 сценариев
    defects             list[str]             "missing_amount", …

DocumentRecord
    document_id   str            sha256 содержимого
    path          Path
    kind          Literal["credit_agreement","audit_notes","kyc",
                          "compliance","operations","unknown","non_document"]
    scenario_id   str | None
    edition       Literal["current","superseded","draft","unknown"]
    text          str
    confidence    float

CovenantRule                     заменяет CovenantSpec
    scenario_id   str
    clause        str            "6.1" — ключ ячейки, приходит из шаблона
    raw_text      str
    period        tuple[date,date]
    metric        MetricExpr     дерево над КАТЕГОРИЯМИ, не над колонками
    comparator    str
    threshold     Decimal
    threshold_kind Literal["amount","ratio","percent"]
    trigger       MetricExpr | None    для springing-тестов
    trust         Literal["accepted","revised","low"]

CellAnswer
    scenario_id, clause
    status        Literal["COMPLIANT","BREACH"]
    actual        Decimal        всегда > 0, 2 знака
    evidence_txn_id str | None
    # не сериализуется, для разбора
    confidence, flags, calculation_id
```

### Почему категория — поле сущности, а не выражение фильтра

Решающий довод из данных **[OBS]**: аудиторская записка формулируется как
«первоначально учтённая как *Операционные расходы*, переклассифицирована как *Страховые премии*».
Механизм переклассификации имеет смысл **только если у операции есть категория**. Предметная
область мыслит категориями операций; значит, категория — атрибут `LedgerEntry`, а не предикат
внутри правила.

Это и есть исправление ошибки границы абстракции, найденной в [STAGE 3 §2.1](23_STAGE3_GAP_ANALYSIS.md).

### `MetricExpr` — выражение над категориями

```
MetricExpr :=
    Aggregate(op, category_set, sign_filter, extra_predicates)
  | Ratio(numerator: MetricExpr, denominator: MetricExpr)
  | Difference(MetricExpr, MetricExpr)
  | LargestLine(category_set)          «наибольшая статья»
  | Constant(Decimal)
```

Минимально достаточно для наблюдаемых типов ковенантов: агрегаты, коэффициенты,
«выручка минус наибольшая накладная статья», доли от выручки.
`sign_filter` необходим, потому что **знак не равен направлению** — контр-проводки требуют
явного выбора «только списания» / «только поступления» / «все».

## 4. Контракты и поведение по этапам

### A1 `ingest_ledger`

- **RESP** CSV → строки, побайтово верно. Никакой интерпретации.
- **IN** `master_ledger_2025.csv` (CRLF, UTF-8, 7 колонок)
- **OUT** `RawLedgerRow[]` + `source_sha256`
- **ERROR** Нечитаемый файл → **FATAL**. Строка с лишним/недостающим полем → в карантин с
  сохранением исходного текста.
- **OBS** число строк, sha256, число карантинных
- **IDEMP** по sha256 файла; повторный запуск пропускает
- **DEPS** stdlib csv
- **TEST** фикстуры: CRLF, BOM/без BOM, пустая ячейка, лишняя запятая, EUR

### A2 `ingest_documents`

- **RESP** Файлы → текст. Отбор по типу файла, не по расширению.
- **IN** `documents/` (200 PDF, 1 CSV, 1 TXT, 1 `.db`)
- **OUT** `RawDocument{document_id=sha256, path, text, page_count, has_text_layer}`
- **ERROR** Не-PDF → `kind="non_document"`, **не ошибка**. PDF без текстового слоя → OCR, если
  доступен; иначе `text=""` и пометка. Битый PDF → карантин.
- **OBS** `has_text_layer` по каждому; ожидается 199/200
- **IDEMP** по sha256 содержимого
- **DEPS** PyMuPDF; OCR опционально
- **TEST** реальный корпус: 200 файлов должны дать 199 с текстом и 3 `non_document`

### A3 `load_template`

- **RESP** Шаблон → **манифест ожиданий**. Единственный источник списка ячеек.
- **IN** `submission_template.json`
- **OUT** `CellKey[36]` = `(scenario_id, clause)`
- **ERROR** Нечитаемый или пустой → **FATAL**: без него нечего заполнять
- **OBS** число ячеек, перечень сценариев
- **IDEMP** чистая функция
- **TEST** контрактный: ключи выхода ≡ ключи шаблона

### B1 `route_documents` ★ новый ★

- **RESP** Определить по **тексту**: тип, сценарий, редакция. Закрывает ловушку приманок.
- **IN** `RawDocument`
- **OUT** `DocumentRecord{kind, scenario_id, edition, confidence}`
- **ERROR** Не удалось определить → `kind="unknown"`, документ **не используется**, но
  записывается. Не фатально.
- **OBS** распределение по типам; **обязательный инвариант: ровно 12 документов
  `kind=credit_agreement, edition=current`**, по одному на сценарий. Отклонение — сигнал тревоги.
- **IDEMP** по `document_id`
- **DEPS** правила по маркерам (`ИСПОЛНИТЕЛЬНЫЙ ЭКЗЕМПЛЯР`, `НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ`, `ПРОЕКТ —`)
  + LLM как запасной путь при неоднозначности
- **TEST** золотой набор: 12 действующих договоров, ≥5 недействующих, 19 аудитов, 19 KYC
- **Стратегия** Правила первыми, модель — только на остатке. Маркеры наблюдаемы **[OBS]** и
  дёшевы; модель нужна там, где маркера нет.

### B2 `extract_clauses`

- **RESP** Из действующего договора взять «Статью 6» → тексты пунктов 6.1–6.3.
- **IN** `DocumentRecord{kind=credit_agreement, edition=current}`
- **OUT** `ClauseText{scenario_id, clause, text, period}`
- **ERROR** Пункт не найден → пустой текст, ячейка пойдёт по деградированному пути. Не фатально.
- **OBS** найдено пунктов из ожидаемых 36
- **IDEMP** по `document_id`
- **TEST** на 12 реальных договорах: 36 из 36 пунктов

### B3 `extract_adjustments` ★ новый ★

- **RESP** Из аудиторских примечаний извлечь **применённые** переклассификации, отсеяв
  рассмотренные-и-отклонённые.
- **IN** `DocumentRecord{kind=audit_notes, edition=current}`
- **OUT** `Reclassification{target: txn_id | (amount, counterparty), from_cat, to_cat, applied: bool, rationale}`
- **ERROR** Неоднозначная цель → `applied=false` + запись проблемы. **Отказ вместо угадывания.**
- **OBS** извлечено / применено / отклонено — по каждому сценарию
- **CRITICAL** Извлекать **все** упоминания вместе с признаком применения. Наивный сбор `txn_id`
  применит `(7.2)` и `(8.1)`, которые применять нельзя **[OBS]**.
- **TEST** на `4db1d630055f.pdf`: ровно 1 применённая, 2 отклонённые

### B4 `extract_parties` ★ новый ★

- **RESP** Из KYC: таблица долей + **порог из текста досье** → перечень связанных сторон.
- **IN** `DocumentRecord{kind=kyc}`
- **OUT** `RelatedPartySet{entities: [(name, share)], threshold, resolved: [name]}`
- **ERROR** Порог не найден → **не подставлять умолчание**, пометить сценарий. Подстановка 20 %
  по догадке — ровно та ошибка, из-за которой переписывается проект.
- **OBS** порог по каждому досье; отклонение от 20 % — к разбору
- **CRITICAL** Порог наблюдаем как «20.0 % и более» на одном досье **[OBS]**; одинаков ли он
  во всех — **[UNK] K-10**. Читать из текста, а не хардкодить.
- **TEST** на ACC-7801: 34.5 % → связанная, 18.7 % и 6.2 % → нет

### B5 `categorize` ★ новый, центральный ★

- **RESP** `description` → `Category`.
- **IN** `LedgerEntry` (673 значимые строки)
- **OUT** `category`, `category_source`, `category_confidence`
- **ERROR** Не удалось → `category=None`, строка **не исчезает**; попадёт в агрегат только если
  правило допускает `None`. Иначе — в отчёт разбора.
- **OBS** распределение по категориям; доля `None`; доля низкой уверенности
- **IDEMP** по `hash(description)` — 624 уникальных текста на 673 строки **[OBS]**, кеш
  экономит ~7 % и делает повтор бесплатным
- **DEPS** таксономия категорий **[UNK] K-01**
- **CRITICAL** Контр-проводки: `Payroll clearing account sweep back`, `Utility deposit returned`,
  `Water charge adjustment credit`, `Payroll advance recovered` — положительные суммы, но это
  **возвраты расходов, а не выручка** **[OBS]**. Категория обязана это различать; наивное правило
  «плюс ⇒ выручка» даёт ошибку в разы и обнуляет ячейку.
- **TEST** Золотой набор из ≥40 описаний, включая все обнаруженные контр-проводки. **Порог
  приёмки формулируется от последствий:** ошибка категоризации, сдвигающая `actual` более чем на
  5 %, недопустима.
- **Стратегия** Таксономия выводится из корпуса на отдельном шаге и фиксируется как артефакт с
  версией — не хардкодится в коде.

### B6 `compile_rule`

- **RESP** `ClauseText` → исполняемое `CovenantRule` над категориями.
- **IN** `ClauseText`, таксономия, каталог допустимых операций
- **OUT** `CovenantRule`
- **ERROR** Схема не прошла валидацию → починка ≤2 попыток → иначе `trust="low"`, но правило
  **всё равно строится** по наилучшей догадке (Ф-2).
- **OBS** доля успешных компиляций, число починок
- **IDEMP** по `hash(clause_text + версия таксономии)`
- **CRITICAL** **Граница LLM сохраняется**: модель выбирает категории и операции **из закрытого
  каталога**, не пишет SQL и не называет чисел, кроме порога из текста пункта.
- **TEST** на 36 реальных пунктах: доля компилируемых; сверка порогов с текстом

### B7 `review_rule`

- **RESP** Проверить соответствие правила тексту пункта до вычисления.
- **IN** `CovenantRule` + `ClauseText` + таксономия
- **OUT** `accepted | objection` → одна ограниченная перекомпиляция
- **ERROR** Отклонено дважды → `trust="low"`, ячейка **считается всё равно**
- **OBS** доля отклонений, доля исправленных
- **CRITICAL** Тип решения не содержит полей `status`/`actual`/`evidence` — числа на этом шаге
  ещё не существует (принцип из Cloud1, подтверждается реальными ловушками)
- **TEST** заглушки ревьюера; проверка жёстких границ цикла

### C1 `normalize_ledger`

- **RESP** `RawLedgerRow` → `LedgerEntry`. Только детерминированные преобразования.
- **IN** `RawLedgerRow[]`
- **OUT** `LedgerEntry[]`
- **Правила**
  ```
  scenario_id := txn_id.split('-')[1]                      детерминированно
  is_noise    := scenario_id ∉ 12 сценариев шаблона        800 из 1473 [OBS]
  amount      := Decimal, знак СОХРАНЯЕТСЯ
  amount_usd  := конвертация EUR → USD                     [UNK] K-02
  defects     := ["missing_amount"] для 2 строк [OBS]
  ```
- **ERROR** Пустая сумма → **не отбрасывать**: `amount=None`, `defects=["missing_amount"]`.
  Решение о судьбе принимает правило, а не загрузчик.
- **OBS** значимых / шумовых; дефектных; EUR
- **IDEMP** чистая функция от raw
- **TEST** свойство: `∀ raw: normalize(raw)` не теряет ни одной строки

### C2 `apply_adjustments`

- **RESP** Применить **утверждённые** переклассификации и признак связанной стороны.
- **IN** `LedgerEntry[]`, `Reclassification[]`, `RelatedPartySet`
- **OUT** `LedgerEntry[]` с обновлёнными `category`, `category_source="audit"`, `is_related_party`
- **ERROR** Цель не найдена в реестре → запись проблемы, изменения нет
- **OBS** применено корректировок; сколько целей не разрешилось
- **IDEMP** порядок применения фиксирован; повтор даёт тот же результат
- **CRITICAL** Применяются **только** `applied=true`. Сопоставление `counterparty` со связанными
  сторонами — **[UNK] K-04**: точное или нечёткое. До разрешения — точное, с записью почти-совпадений.
- **TEST** на P10: применяется `(7.1)`, не применяются `(7.2)` и `(8.1)`

### C3 `evaluate`

- **RESP** `CovenantRule` + `LedgerEntry[]` → `actual`, `status`. **LLM не участвует.**
- **IN** правило, записи сценария, период
- **OUT** `actual: Decimal > 0`, `status`, `calculation_id`
- **Правила**
  ```
  выборка := записи сценария ∧ период ∧ категории правила ∧ sign_filter
  actual  := |значение метрики|                     всегда модуль [CASE]
  status  := COMPLIANT | BREACH по comparator
  для springing: сначала trigger, при несрабатывании — COMPLIANT,
                 но actual всё равно вычисляется и указывается [CASE]
  ```
- **ERROR** Пустая выборка → `actual=0`, флаг `empty_selection`, **status вычисляется** от 0.
  SQL-ошибка → флаг, `status` берётся по наилучшей догадке (Ф-2).
- **OBS** `input_row_count`, SQL, параметры — в `Calculation`
- **IDEMP** чистая функция; при фиксированных входах побитово воспроизводима
- **TEST** сверка всех 36 `actual` с `ground_truth.json` по шкале 5 %

### C4 `find_evidence` ★ новый, заменяет селекторы ★

- **RESP** Найти операцию, чьё изменение переворачивает вердикт.
- **IN** правило, записи, базовый `status`
- **OUT** `evidence_txn_id | None`
- **Алгоритм** — прямая реализация определения из CASE:
  ```
  если status == COMPLIANT:            → None      [OBS] все 9 улик у BREACH
  кандидаты := записи, затронутые ИНТЕРПРЕТАЦИОННЫМ решением:
      · вошедшие в метрику
      · переклассифицированные аудитом
      · помеченные как связанная сторона
      · имеющие дефект (пустая сумма)
  для каждого кандидата:
      пересчитать метрику БЕЗ него
      если status меняется → кандидат определяющий
  ровно один      → он
  ноль            → None    (результат не определяется одной операцией)
  больше одного   → None + запись проблемы   отказ вместо угадывания
  ```
- **ERROR** Никогда не фатально: `None` — допустимый ответ и стоит 0.20 только там, где ключ не `null`
- **OBS** размер набора кандидатов, число определяющих
- **СТОИМОСТЬ** ≤59 пересчётов на ячейку, чистый SQL — пренебрежимо
- **TEST** сверка с 9 известными уликами эталона; для P5/P7/P9 6.3 проверяется тождество
  `actual == |amount(evidence)|` **[OBS]**

### C5 `verify`

- **RESP** Независимая перепроверка перед выдачей.
- **Проверки**
  ```
  полнота        36 ячеек присутствуют      ← манифест из шаблона (A3)
  двойной путь   пересчёт другим кодом      ← критично при допуске 5 %
  границы        actual > 0, 2 знака, status ∈ {COMPLIANT, BREACH}
  улика          evidence_txn_id существует в реестре и принадлежит сценарию
  ```
- **ERROR** Расхождение двойного пути → флаг `unreliable`, ячейка **всё равно выдаётся**
- **OBS** число проблем по типам; ранг разбора
- **TEST** намеренно испорченные результаты должны отлавливаться

### C6 `emit`

- **RESP** Заполнить шаблон. **Не создавать и не переименовывать ключи.**
- **IN** `CellAnswer[36]`, шаблон
- **OUT** `submission.json`
- **ERROR** Отсутствует ячейка → заполняется деградированным ответом (Ф-2), **никогда не пропуск**
- **Правила** `actual` — 2 знака; `status` — заглавными; верхнеуровневые `team`/`contact_email`/`model`
- **TEST** контрактный: множество ключей выхода ≡ множеству ключей шаблона; тип каждого поля

## 5. Error strategy

### FATAL — прогон невозможен

```
шаблон нечитаем или пуст            нечего заполнять
реестр нечитаем целиком             нечего считать
```

Всего два случая. Всё остальное деградирует.

### QUARANTINE — запись сохраняется, из расчёта исключается

```
строка реестра с неразбираемой структурой   сохраняется исходный текст
битый PDF                                    сохраняется путь и ошибка
документ с kind="unknown"                    не используется, но виден
```

### DEGRADE — ответ выдаётся, качество помечается

```
пункт не извлечён          → правило-заглушка, trust="low"
правило не скомпилировано  → наилучшая догадка, trust="low"
категория не определена    → category=None, поведение решает правило
пустая выборка             → actual=0, флаг empty_selection
расхождение двойного пути  → флаг unreliable
улика неоднозначна         → None
```

Все три уровня — прямое следствие Ф-2: **пустая ячейка стоит столько же, сколько неверная,
поэтому система обязана всегда отвечать.**

### Что сохраняется между запусками

| Артефакт | Зачем |
| --- | --- |
| `raw_ledger_rows`, `raw_documents` | воспроизводимость от источника |
| `DocumentRecord` с решением о редакции | самое дорогое и самое рискованное решение |
| `Category` по хешу описания | 624 уникальных текста; кеш делает повтор бесплатным |
| `Reclassification`, `RelatedPartySet` | результат разбора документов |
| `CovenantRule` + история починок | недетерминизм локализован здесь |
| `Calculation` (SQL, параметры, число строк) | двойной путь и разбор расхождений |
| Отчёт уверенности | приоритет ручной проверки 36 ячеек |

### Повторная обработка

```
фаза A   идемпотентна по sha256 источника
фаза B   идемпотентна по (document_id | hash(текст)) — все вызовы LLM кешируются
фаза C   чистая: при фиксированных правилах и записях результат побитово тот же
```

Практически: повторный прогон без изменения входов **не обращается к LLM вообще** и даёт
идентичный `submission.json`.

## 6. Где что живёт

| Вопрос | Ответ | Обоснование |
| --- | --- | --- |
| Где валидация | На каждой границе как проверка контракта pydantic; отдельного этапа нет | Валидация — свойство перехода, а не шаг |
| Где нормализация | Только C1, детерминированно | Единственное место, где raw становится domain |
| Где бизнес-правила | В `CovenantRule` (данные) и в C3 (исполнитель) | Правила приходят из документов, значит это данные, а не код |
| Где неполные записи | Помечаются в C1, судьбу решает правило в C3 | Загрузчик не знает, важна ли строка для конкретного ковенанта |
| Где интерпретация | Только фаза B | Единственная фаза с LLM; граница проверяема |
| Где недетерминизм | Только B6 (компиляция) | Всё остальное — чистые функции |

```
4  evaluators: MetricExpr вместо MetricSpec; арифметика не трогается
5  фаза A: загрузка реальных источников
6  фаза B: маршрутизация, извлечение, категоризация, компиляция
7  фаза C: расчёт, улика, верификация, выдача
8  скоринг по ground_truth.json
9  CLEANUP по порядку из STAGE 3 §6
```

## 9. Что остаётся неизвестным и как проектирование это выдерживает

| ID | Неизвестное | Как учтено в проекте |
| --- | --- | --- |
| **K-01** | Перечень категорий | Таксономия — **артефакт с версией**, выводится из корпуса отдельным шагом; правила ссылаются на её версию. Смена таксономии не трогает код |
| **K-02** | Курс EUR→USD | `amount_usd` — отдельное поле; политика конвертации — параметр C1, а не зашитая константа |
| **K-03** | Пустые суммы | `defects=["missing_amount"]`, решение принимает правило в C3 |
| **K-04** | Сопоставление контрагентов | C2 начинает с точного совпадения и **записывает почти-совпадения**; переход к нечёткому — по данным, не по догадке |
| **K-05** | Определение EBITDA | Если задано в договоре — попадёт в `MetricExpr` как `Difference`; если нет — ячейка пойдёт `trust="low"` и будет видна в разборе |
| **K-07** | Универсальность маркера редакции | B1 проверяет инвариант «ровно 12 действующих договоров»; нарушение — громкий сигнал |
| **K-08** | Единственный PDF без текста | A2 помечает `has_text_layer=false`; судьба OCR решается фактом, а не заранее |
| **K-10** | Порог связанной стороны | B4 **читает порог из текста**, умолчание запрещено |

Ни одно неизвестное не зашито в структуру. Каждое локализовано в одном этапе и параметризовано.

## 10. Итог

**Proposed architecture** — три фазы, 16 этапов, один процесс. Фаза A детерминированно загружает,
фаза B единственная обращается к LLM и производит интерпретацию, фаза C детерминированно считает
и выдаёт. Ни API, ни сервисов, ни очередей: потребитель один — автоматический скорер.

**Ключевое отличие от прежней архитектуры** — граница абстракции проведена по предметной области,
а не по формату источника: **категория операции стала атрибутом сущности**, а правило ковенанта
говорит на языке категорий, а не колонок таблицы.

**Второе отличие** — улика вычисляется контрфактическим перебором, буквально по определению из
условия задачи, и это подтверждено эталоном на трёх ячейках **[OBS]**.

**Третье** — из правила «пустая ячейка стоит столько же, сколько неверная» выведена вся стратегия
ошибок: два фатальных случая, всё остальное деградирует до ответа.
