## 0. Формальная постановка

### 0.1 Обозначения

| Символ | Значение | Оценка на приватном датасете |
| --- | --- | --- |
| `D` | документов PDF | 10 … 100 |
| `P` | страниц суммарно | 100 … 2 000 |
| `C` | различных ковенантов после дедупликации | 20 … 200 |
| `B` | заёмщиков | 5 … 50 |
| `N` | строк транзакций | 10⁴ … 10⁷ |
| `Q` | вопросов организатора | 20 … 200 |
| `T` | глобальный бюджет времени | **10 800 с** |

### 0.2 Контракт системы

```
вход:   Документы 𝒟 = {d₁…d_D},  Реестр транзакций 𝒯 (|𝒯| = N),  Вопросы 𝒬 = {q₁…q_Q}
выход:  Ответы 𝒜 = {a₁…a_Q},  где aᵢ = ⟨verdict, number, evidence, source_id⁺⟩
```

### 0.3 Инварианты (нарушение = провал, не деградация)

```
И1  ∀ q ∈ 𝒬 : ∃ a ∈ 𝒜 с a.question_id = q.id
    — на каждый вопрос есть ответ. Отсутствие строки запрещено;
      статус "failed" разрешён.

И2  ∀ a ∈ 𝒜 : a.number вычислено детерминированным кодом,
    не текстом модели.  Формально: ∄ путь данных LLM → number.

И3  ∀ a ∈ 𝒜 : a.source_id ≠ ∅ ∧ resolve(a.source_id) → (document_id, page, block_id)
    — traceability 100%, ссылка разрешима.

И4  ∀ (𝒟, 𝒯, spec) фиксированных : выполнение дважды даёт
    побитово идентичный 𝒜.  Недетерминизм локализован в компиляции.

И5  wall_clock(инжест + прогон) ≤ T = 10 800 с
```

**И1 сейчас не выполняется.** Система перечисляет найденные ковенанты, а не отвечает на вопросы.
Это дефект №1 плана (см. [§3.1](#31-p0-1--вопросы-как-обязательный-вход)).

## 1. Бюджет времени: почему 3 часа — это узко

### 1.1 Декомпозиция

```
T = T_ingest + T_compile + T_review + T_evaluate + T_serialize
```

| Компонент | Формула | При C=50, P=500 | Доля |
| --- | --- | --- | --- |
| `T_ingest` | `P × t_page` | 500 × 2 с = **1 000 с** | 9 % |
| `T_compile` | `C × k_c × t_llm / K` | 50 × 3 × 90 / K | ← критично |
| `T_review` | `C × k_r × t_llm / K` | 50 × 2 × 90 / K | ← критично |
| `T_evaluate` | `Q × t_sql` | 200 × 0.05 с = **10 с** | 0.1 % |
| `T_serialize` | `O(Q)` | < 1 с | ~0 |

где `k_c ≤ 3` (компиляция + до 2 починок), `k_r ≤ 2` (ревью + после перекомпиляции),
`t_llm = 90 с` (текущий тайм-аут), `K` — степень параллелизма.

### 1.2 Расчёт требуемого параллелизма

Последовательное исполнение (`K = 1`), худший случай:

```
T_llm = C × (k_c + k_r) × t_llm = 50 × 5 × 90 = 22 500 с = 6 ч 15 мин
```

**Превышение бюджета в 2.08 раза.** При `C = 200` — в 8.3 раза.

Требование к `K`:

```
C × (k_c + k_r) × t_llm / K  ≤  T − T_ingest − T_evaluate − T_serialize
50 × 5 × 90 / K              ≤  10 800 − 1 000 − 10 − 1  =  9 789
K                            ≥  22 500 / 9 789  =  2.30
```

С запасом ×3 на медленные ответы и повторы: **`K = 8`**.

При `C = 200`: `K ≥ 9.2` → **`K = 16`** и обязательный ранний выход по дедлайну.

### 1.3 Вывод

| Требование | Статус |
| --- | --- |
| Параллельная компиляция и ревью, `K = 8…16` | **отсутствует** — код последовательный |
| Глобальный дедлайн с graceful degradation | **отсутствует** |
| Измерение `t_page` и `t_llm` на реальных данных | **отсутствует** |

Это P0. Без этого система при `C > 25` не укладывается в регламент независимо от качества ответов.

## 2. Контракты узлов графа

Формат: `вход → выход`, бюджет, режим отказа, откат.

### 2.1 Узел `INGEST_PDF`

```
вход:   path: Path
выход:  list[DocumentBlock]
бюджет: t_page ≤ 3 с (GPU) | ≤ 15 с (CPU);  жёсткий тайм-аут 30 с/страница
```

| Отказ | Обнаружение | Откат |
| --- | --- | --- |
| Страница не рендерится | исключение fitz | запись `ingestion_artifacts(status=failed)`, **страница НЕ исчезает** |
| Таблица не распознана `layout`-провайдером | `visual.extract()` бросает / вернул 0 блоков | **★ откат к сырому тексту страницы** — новый путь |
| OCR превысил тайм-аут | wall clock > 30 с | откат к `native`-тексту, метка `degraded` |
| Все пути упали | — | блок-заглушка с `route=failed`, попадает в манифест как пробел |

**Текущее состояние цепочки:** `native → layout → ocr → failed`. Отката `layout → native` нет —
это ровно та уязвимость, которую ты назвал: сломанная таблица → уверенная галлюцинация.

**Целевая цепочка:**

```
native ─┬─ ok ────────────────────────────────► blocks
        └─ мало текста ─► layout ─┬─ ok ──────► blocks (structured)
                                  └─ fail ──┬─► native_raw (★ новый откат)
                                            └─► ocr ─┬─ ok ─► blocks (degraded)
                                                     └─ fail ─► failed_marker
```

### 2.2 Узел `DETECT`

```
вход:   list[DocumentBlock]
выход:  list[CovenantCandidate]
бюджет: O(P), < 5 с суммарно — регулярки, не узкое место
```

| Отказ | Откат |
| --- | --- |
| Ноль кандидатов на документе с ковенантами | **нижняя граница полноты**: все блоки в секции с заголовком «Ковенанты / Обязательства / Financial covenants» → кандидаты |
| Язык не EN/RU/KZ | лог `unsupported_language`, блок всё равно в кандидаты, если есть цифра + модальность |

Асимметрия стоимости — обоснование агрессивной рекалл-стратегии:

```
цена ложноположительного = 1 вызов LLM ≈ 90 с / K ≈ 11 с
цена ложноотрицательного = 1 потерянный ответ = полный балл за пару, невидимо
⟹ порог смещать в сторону recall
```

### 2.3 Узел `COMPILE`

```
вход:   CovenantCandidate, document_context
выход:  CovenantSpec | failed
бюджет: k_c × t_llm ≤ 270 с на кандидата;  при K=8 — 34 с амортизированно
```

| Отказ | Обнаружение | Откат |
| --- | --- | --- |
| Модель вернула невалидный JSON | pydantic ValidationError | repair-цикл, ≤ 2 попытки |
| Поле вне каталога | `validate_compiled_spec` | repair с явным списком `FILTER_FIELDS` |
| Тайм-аут API | 90 с | 1 ретрай, затем `status=failed_compilation` |
| 3 попытки исчерпаны | `attempt ≥ 3` | `status=failed_compilation`, **пара остаётся в манифесте** |

### 2.4 Узел `SPEC_REVIEW` (Critic)

```
вход:   CovenantSpec, raw_text, FILTER_FIELDS
выход:  SpecReviewDecision{accepted, confidence, objection}
бюджет: k_r × t_llm ≤ 180 с;  при K=8 — 23 с амортизированно
```

**Ответ на твоё возражение «Critic не разрешит глубокие противоречия zero-shot».** Согласен —
поэтому область его ответственности сужена по построению:

| Critic **проверяет** | Critic **не проверяет** |
| --- | --- |
| соответствие одного пункта одной спецификации | противоречия **между** документами |
| наличие поля в каталоге | приоритет версий |
| тип метрики vs формулировка | арифметику |
| полноту переноса ограничений | данные транзакций |

Межверсионные конфликты решает `TemporalEvaluationService` детерминированно — он **отказывается**
разбивать агрегаты через смену версии, а не угадывает. Critic туда не допущен.

Защита от зацикливания — структурная, а не эвристическая:

```
recompile_count ≤ 1     (в коде: линейный вызов, не цикл — spec_review_service.py:71)
отклонение дважды       → spec_trust="low", ковенант ВСЁ РАВНО оценивается
⟹ верхняя граница вызовов на ковенант = k_c + k_r = 5, достижима, доказуема
```

### 2.5 Узел `ENTITY_LINK`

```
вход:   text | transaction_row
выход:  list[borrower_id]
бюджет: O(1) на строку, индекс в памяти
```

| Отказ | Откат |
| --- | --- |
| Имя не разрешилось точным совпадением | 3-уровневый резолвер: ID → идентификаторы (БИН) → нормализованное имя (rapidfuzz) |
| Неоднозначность (2+ кандидата) | **отказ, а не выбор**: `status=ambiguous`, пара в манифест с флагом |
| **MCC-код / тариф не найден** | **★ узла не существует** — см. [§3.4](#34-p1-2--каталог-mcc-и-тарифов) |

### 2.6 Узел `EVALUATE`

```
вход:   CovenantSpec, borrower_id, date
выход:  CovenantResult{verdict, number, evidence}
бюджет: t_sql ≤ 200 мс при N ≤ 10⁶;  при N > 10⁶ — индекс по (borrower_id, transaction_date)
```

Вызовов LLM: **0**. Это инвариант И2, обеспеченный конструкцией.

| Отказ | Откат |
| --- | --- |
| `duckdb.Error` | `FailureStage.EVALUATION`, `status=failed`, строка сохраняется |
| Пустая выборка (`input_row_count = 0`) | флаг `empty_input_rows` → `confidence=medium`, не молчаливый ноль |
| Метрика NULL | `Decimal("0.000000")` для SUM, `None` для MAX/MIN |

### 2.7 Узел `VERIFY`

```
вход:   CovenantResult, Calculation, ExpectationManifest
выход:  list[VerificationIssue]
бюджет: +1 SQL на пару ≈ 200 мс
```

| Проверка | Оракул | Независим? |
| --- | --- | --- |
| двойной путь числа | перевыполнение `Calculation.sql` вне классов-вычислителей | **да** |
| полнота | `expectation_manifest`, построен до оценки | **да, если есть 𝒬** |
| доказательство | независимый перевывод `EvidenceValidator` | **да** |
| вердикт vs оператор | `compare()` из того же числа | нет — замкнут, но дёшев |

## 3. Приоритезированный бэклог

Обозначения: **P0** — без этого регламент не выполняется; **P1** — риск потери баллов;
**P2** — улучшение.

### 3.1 P0-1 — Вопросы как обязательный вход

**Проблема.** Инвариант И1 нарушен. `evaluate-all` перечисляет найденные ковенанты. Вопрос, под
который ковенант не найден, не даёт строки в ответе — тихий ноль.

**Решение.**

```
𝒬 → обязательный аргумент evaluate-all (не флаг)
для каждого q ∈ 𝒬:
    найти spec по (borrower_id, covenant_id)
    найдено      → оценить
    не найдено   → строка со status="unresolved_covenant", verdict="unknown"
                   ⟹ строка ЕСТЬ, инвариант И1 держится
пары вне 𝒬 → оцениваются, помечаются supplementary
```

**Объём.** `cli.py` + `pipeline/evaluate.py`, ~120 строк. **Оценка: 3 ч.**

### 3.2 P0-2 — Параллелизм и глобальный дедлайн

**Проблема.** `T_llm = 22 500 с` при `C=50, K=1` против бюджета `9 789 с`. Превышение ×2.08.

**Решение.**

```python
# пул на компиляцию + ревью
K = min(16, max(4, ceil(C × 5 × t_llm / T_llm_budget)))

# глобальный дедлайн с деградацией
deadline = start + T_budget
если now() > deadline − T_reserve:
    прекратить компиляцию новых кандидатов
    оставшиеся → status="deadline_exceeded", остаются в манифесте
    перейти к EVALUATE с тем, что скомпилировано
```

`T_reserve = T_evaluate + T_serialize + 300 с` — гарантия, что ответ будет сформирован всегда.

**Объём.** `ThreadPoolExecutor` в `preprocess.py`, класс `DeadlineGuard`. ~180 строк.
**Оценка: 5 ч.**

### 3.3 P1-1 — Откат при поломке таблицы

**Проблема.** Названа тобой как критическая: парсер ломает структуру банковской таблицы → RAG
выдаёт уверенную галлюцинацию. Проверено: отката `layout → native_raw` в коде нет.

**Решение.**

```
try:    blocks = visual.extract(page)
        assert структурная целостность:
            len(blocks) > 0
            ∧ доля ячеек с непустым текстом ≥ 0.5
            ∧ число колонок стабильно по строкам (σ/μ ≤ 0.2)
except / assert fail:
        blocks = [native_raw_block(page)]
        block.extraction_mode = "degraded_raw"
        ⟹ компилятор ВИДИТ метку degraded и снижает confidence
```

Ключевое: деградация **видима компилятору и ревьюеру**, а не скрыта.

**Объём.** `ingestion/pdf.py` + валидатор целостности таблицы. ~140 строк. **Оценка: 4 ч.**

### 3.4 P1-2 — Каталог MCC и тарифов

**Проблема.** Твой пункт 2 бэклога — кросс-референсинг тарифов, лимитов и MCC. В коде **ноль
упоминаний**. Если приватный датасет их содержит, узел отсутствует целиком.

**Решение — расширение закрытого каталога, не обход его.**

```
transaction_fields.py:
    PHYSICAL_TRANSACTION_FIELDS ∪= {mcc_code, tariff_id, product_code}

новая таблица reference_catalog(catalog_type, code, attributes JSON)
    загружается из CSV/XLSX реестра тем же путём, что транзакции

FilterSpec поддерживает:  mcc_code IN (5411, 5812)
JOIN с reference_catalog — детерминированный, в sql/builder.py
```

Инвариант И2 сохраняется: LLM выбирает **код из каталога**, не пишет SQL.

**Риск, который я обязан назвать:** это спекулятивная работа. Мы не знаем, есть ли MCC в приватном
датасете. Делать до того, как увидим данные, — ставка. **Рекомендация: заготовить схему и загрузчик
(2 ч), реализацию фильтров отложить до просмотра датасета.**

**Объём.** Схема + загрузчик: 2 ч. Фильтры: +3 ч, только по факту.

### 3.5 P1-3 — Инструментирование latency

**Проблема.** Твоё замечание про отсутствие количественных метрик. Единственный тайм-аут в
системе — 90 с на вызов LLM (`config.py:26`).

**Решение.**

```
на каждый trace_stage: t_start, t_end, t_wall
агрегаты в pipeline_stage_records:
    p50, p95, p99, max по каждому узлу
экспорт: metrics.json после прогона

пороги алерта:
    t_page      p95 > 5 с   → OCR деградировал
    t_llm       p95 > 60 с  → снизить K или увеличить тайм-аут
    t_sql       p95 > 500 мс → нужен индекс
    T_total     > 0.8 × T   → включить раннюю деградацию
```

**Объём.** `observability/timing.py`. ~90 строк. **Оценка: 2 ч.**

### 3.6 P1-4 — Синтетические edge-кейсы

**Проблема.** Твоё требование: покрыть пайплайн тестами на синтетических edge-кейсах до 9 августа.
Сейчас есть `synthetic/regression_v2.py` (426 строк), но он проверяет happy path.

**Целевой корпус — 24 кейса, по 4 на класс:**

| Класс | Кейсы |
| --- | --- |
| **Таблицы** | объединённые ячейки; перенос через страницу; вложенная шапка; пустая колонка |
| **Версии** | поправка задним числом; две правки в один день; бессрочная + срочная; отмена |
| **Сущности** | омонимичные имена; смена наименования; заёмщик только по БИН; групповой ковенант |
| **Формулировки** | качественный запрет без цифры; двойное отрицание; «не более X, кроме Y»; отношение с нулевым знаменателем |
| **Данные** | пустая выборка; одна строка; NULL в amount; смешанные валюты |
| **Язык** | KZ; смешанный RU/EN; транслитерация; юникод-омоглифы |

Каждый кейс: вход + эталонный ответ + **ожидаемая деградация** (какой откат обязан сработать).

**Объём.** ~600 строк фикстур + тесты. **Оценка: 8 ч.**

### Про R3 — твоё «главное скрытое допущение»

Ты прав, что допущение о похожести приватного датасета на открытый — скрытое и опасное. Способ
снять его не в том, чтобы угадать структуру, а в том, чтобы **тестировать классы деформаций, а не
конкретный профиль данных**. Отсюда шесть классов в §3.6 вместо расширения существующего
happy-path корпуса.

Остаточный риск честно помечен как средний: полностью снять его нельзя, пока данные не увидены.

### Про R8 — не откладывать

Единственный риск со статусом «известна». На текущей машине зависимости не ставятся: Python 3.14,
`pyyaml==6.0.2` не собирается. **Пока это не исправлено, ни один тест из §3.6 не может быть
запущен**, и весь график недействителен. Это блокирующая задача перед всем остальным.
