## 1. Настоящая задача

Источник: [data/raw/CASE.ru.md](2_ARCHITECTURE_COVENANT_MVP/data/raw/CASE.ru.md).

### Контракт вывода

Один файл `submission.json` строго по `submission_template.json`:

```json
"answers": {
  "P1": {
    "6.1": { "status": "COMPLIANT", "actual": 1850000.00, "evidence_txn_id": null },
    "6.2": { "status": "BREACH",    "actual": 5400000.00, "evidence_txn_id": "TXN-P1-0020" }
  }
}
```

| Поле | Требование |
| --- | --- |
| `status` | ровно `COMPLIANT` \| `BREACH`, заглавными |
| `actual` | **положительное** число, 2 знака, в долларах; коэффициенты обычным числом |
| `evidence_txn_id` | **единственная определяющая** транзакция или `null` |

**Размер задачи: 12 сценариев × 3 пункта = 36 ячеек.**

### Шкала оценки

```
status            0.50   неверен → вся ячейка 0
actual            0.30   линейно убывает, ноль при относительной ошибке 5 %
evidence_txn_id   0.20   точное совпадение; если в ключе null — убывает вместе с actual
```

### Семантика доказательства

> Транзакция, чья переклассификация, включение, исключение или исправление **и приводит** к
> нарушению. Уберите её — вердикт изменится.
>
> Транзакция, которая лишь вносит вклад в сумму, доказательством **не является**: ни самая
> крупная, ни последняя перед закрытием периода, ни та, что вывела сумму за порог.

### Эталон доступен

`data/raw/ground_truth.json` содержит все 36 ячеек с ответами (`seed: 42`, `version: v1`).
**Точность измеряется точно, а не оценивается.**

## 2. Реальные данные

### 2.1 Реестр `master_ledger_2025.csv`

```
колонки: txn_id, date, account_id, counterparty, description, amount, currency
строк:   1473   → сценарных 673, шумовых 800
даты:    2025-01-02 … 2025-12-31
счетов:  ~490, из них сценарных 12
```

| Свойство | Значение |
| --- | --- |
| Колонка направления | **отсутствует** — знак суммы: расход `−`, поступление `+` |
| Колонка категории | **отсутствует** — категория только в свободном тексте `description` |
| Валюты | USD 658 / EUR 15 в сценарных строках |
| Пустые суммы | 2 (`TXN-P7-0033`, `TXN-P8-0031`) |
| Дубли `txn_id` | 0 |

Связь заёмщика: `txn_id` = `TXN-{scenario_id}-{n}`, каждый `account_id` ↔ ровно один `scenario_id`.

```
P1…P10 → ACC-7801…ACC-7810
B1     → ACC-7201
B4     → ACC-7204
ACC-9xxx (≈480 счетов, 800 строк) → шум, ни к одному сценарию не относится
```

### 2.2 Документы

```
203 файла: 200 PDF, 1 CSV, 1 TXT, 1 Thumbs.db
843 страницы
199 из 200 PDF имеют текстовый слой; скан — один
имена — непрозрачные хеши, тип и заёмщик видны только изнутри
```

Во всех документах встречаются ровно 12 `account_id` — тех же сценарных. 4–8 документов на
сценарий.

### 2.3 Таксономия документов ★ ключевое ★

| Тип | Признак в тексте | Роль |
| --- | --- | --- |
| Договор — **действующий** | `ИСПОЛНИТЕЛЬНЫЙ ЭКЗЕМПЛЯР · ЗАЁМ № ACC-…` | **источник ковенантов** |
| Договор — **недействующий** | `НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ (2024 г.). Заменена…` | **приманка**: другой период и другие пороги |
| Аудиторский отчёт | `Независимый аудитор Заёмщика` | переклассификации, обязательны к применению |
| Промежуточная ведомость | `ПРОЕКТ — ПРОМЕЖУТОЧНАЯ` | **приманка**: черновик аудита |
| Досье KYC | `Управление финансового мониторинга и комплаенса` | список связанных сторон |
| Процедура комплаенса | `Комплаенс — v3 — Контролируемый документ` | шум |
| Операционные сводки | `Проект «Атлас» — Отчёт о статусе` | шум |

**Проверено:** для `P1` и `P3` существуют обе редакции договора. Недействующая датирована
2024 годом, действующая — 2025. Реестр содержит только 2025 год, поэтому выбор недействующей
редакции даёт период без единой транзакции.

### 2.4 Что требуют сами ковенанты

12 действующих договоров, 36 пунктов, около **19 различных типов** ковенантов. Примеры:

```
P1 6.1  Maximum Capital Intensity Ratio
        капзатраты / (операционные расходы + арендные платежи) ≤ 1.17x
        «Суммы, переклассифицированные аудиторами, учитываются по переклассифицированной
         статье как в числителе, так и в знаменателе»

P1 6.2  Минимальная выручка по категории ≥ $7,100,000
        «суммы, отнесённые к статье в аудированной отчётности с учётом переквалификаций»

P1 6.3  Максимальные платежи связанным сторонам ≤ $450,000
        «Связанные стороны определяются по МСФО (IAS) 24 и сведениям досье KYC»

P3 6.1  Springing Drawdown Leverage Test          ← условный, применяется при срабатывании
P4 6.1  Минимальная скорректированная рентабельность по EBITDA
P8 6.1  Максимальные совокупные обязательства по персоналу
P9 6.1  Максимальная доля активов, переданных неограниченным дочерним обществам
P10 6.2 Минимальная выручка за вычетом наибольшей статьи накладных расходов
B1 6.2  Individual Overhead Line Ceiling
B4 6.1  Минимальная выручка за четвёртый квартал
```

Каждый ковенант требует минимум одного из:

1. **классификации транзакции по категории** из свободного текста `description`
   (выручка, капзатраты, операционные расходы, аренда, персонал, коммунальные, налоги, накладные);
2. **применения переклассификаций аудитора** из отдельного документа;
3. **списка связанных сторон** из досье KYC, сопоставленного с `counterparty`;
4. вычисления производных величин (EBITDA, доли, коэффициенты);
5. проверки условия срабатывания (springing).

## 4. Что из построенного остаётся верным

Не всё нужно выбрасывать. Уцелевшее:

| Компонент | Почему остаётся |
| --- | --- |
| **Двухфазный принцип** «LLM интерпретирует → детерминированный код считает» | Верен и для реальной задачи; более того, здесь он критичнее: `actual` оценивается с точностью 5 % |
| Изоляция сбоев, `FailureStage`, частичные результаты | Пустая ячейка и неверная стоят одинаково — падать нельзя ни на одной |
| Идемпотентность загрузки по SHA-256 | 843 страницы; повторный разбор дорог |
| Прослеживаемость: сохранение SQL, параметров, числа входных строк | Требуется для разбора расхождений с эталоном |
| Ревью спецификации до вычисления (Cloud1) | Идея верна: ошибка интерпретации молчалива. Но проверять нужно другие сущности |
| Наблюдаемость LangSmith со структурой узлов | Пригодна как есть |
| Манифест ожиданий | **Становится тривиальным и обязательным**: 36 ячеек шаблона — готовый манифест |

## 5. Главный вывод стадии

> Текущая система решает задачу «найти в документах правила и посчитать по колонкам реестра».
>
> Реальная задача — «выбрать среди приманок действующий документ, **классифицировать каждую
> транзакцию по категории из свободного текста**, применить переклассификации аудитора,
> достать связанные стороны из KYC, посчитать производные показатели и указать
> **определяющую** транзакцию».

Совпадает только вторая половина — арифметика. Первая половина, включая модель данных
`CovenantSpec`, построена на несуществующих колонках.

Ключевой архитектурный разрыв: **`FilterSpec` работает поверх закрытого каталога физических полей,
а реальная задача требует слоя категоризации, которого в данных нет.**

## 6. Открытые вопросы к следующей стадии

Требуют проверки на стадии DATA MODEL, до всякого проектирования:

1. Какими признаками надёжно отличается действующая редакция от недействующей? Достаточно ли
   строки-маркера, или нужен более общий признак?
2. В каком виде аудиторский отчёт задаёт переклассификации — таблицей, текстом, по `txn_id`?
3. Как в KYC перечислены связанные стороны и как они сопоставляются с полем `counterparty`?
4. Как считать EBITDA — определён ли он в договоре или требует внешнего знания?
5. Что делать с 15 строками EUR: конвертировать (по какому курсу и откуда?), исключать или
   они не попадают в сценарные расчёты?
6. Что делать с двумя пустыми суммами — исключать или брать из документа?
7. Сколько категорий реально требуется и различимы ли они по `description` детерминированно
   или только моделью?
8. Может ли одна транзакция быть «определяющей» по правилу, выводимому детерминированно, или
   это требует поиска перебором (убрать строку → пересчитать → изменился ли вердикт)?
